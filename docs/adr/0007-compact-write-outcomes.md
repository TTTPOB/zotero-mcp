# ADR 0007：精简写入结果、返回实体版本与存储差异警告

- 状态：已采纳
- 决策者：人类（2026-11-11 在评审中逐项选定 A2/A3/A7/A9）；A10 存储差异警告由 Agent（lead，2026-11-11）决定
- 日期：2026-11-11
- 涉及：写工具结果模型、创建与批量写入、MCP 写结果序列化
- 取代范围：ADR 0002 中保留旧聚合字段、未知版本使用 null、批量结果不带版本的部分；其余决定继续有效。

## 背景

写工具同时提供逐项结果与多套聚合字段，单条更新成功也需 293 字符，多数是空值和重复信息。创建结果回显完整原生条目，却没有把已有的实体版本放进逐项结果。创建失败项的错误码是 HTTP 数字，与其余写入错误不一致。批量标签和集合归属修改重复读取同一条目，读回的新版本又被丢弃。

真实 Zotero 10.0.6 的创建响应包含已存储条目的 `key`、`version`、`data`；集合创建也包含实体版本。不存在父条目的笔记创建返回逐项 400，消息为 `Parent item 1/ZZZZZZZZ not found`。附件创建版本和上传后的版本不同，实测为 5 与 6。进一步 live 写入测试发现 Markdown 上传结果版本为 74，紧接着读取已为 75；另一次原生探针上传与连续读取均为 96。这说明上传响应不保证附件随后保持该版本，不能把上传结果当作下一次编辑的可靠版本。

进一步实测：向 book 提交 `publicationTitle: "Some Journal"` 会变为 `extra: "Publication Title: Some Journal"`；向 journalArticle 提交 director 作者角色会存为 author。创建成功项的 `data` 与随后读取的实际数据一致，可用于提示这些差异。thesis 的基础字段 publisher 会映射为 university，属于有效的字段映射。

## 决定

1. **A2：以逐项结果作为唯一批量表示。** 顶层为 `ok`、`status`、`results[]`，单目标工具可带 `key`、`version`、`error`；批量工具不重复顶层 key/version。结果项为 `input_index`、`status`，以及已知的 `key`、`version`、`stage`、`error`。附件用 `key` 表示附件 key。未设置字段省略；模型禁止额外字段，移除原生条目回显和聚合字段。恢复所需的错误信息放在 `error.details`。
2. **A3：创建返回已有的本地实体版本。** `add_items`、`create_note`、`create_collection` 直接取创建响应的版本，不额外读取、不猜测。附件上传后不返回版本，也不增加一次读回；编辑前由调用者读取。`attach_markdown` 复用已有附件时保留读取到的版本。此实现取舍由 Agent（lead）根据上述 74/75 反例在 2026-11-11 确认，符合 A3 的“未知则省略”。
3. **A7：每项错误统一为 `{code, message, retryable, details?}`。** 创建失败的 400/404/412 分别映射到 `INVALID_ARGUMENT`/`NOT_FOUND`/`VERSION_CONFLICT`，其他映射到 `UNKNOWN_ERROR`，保留原消息，数字放在 `details.http_status`。缺失输入结果保留 `UNKNOWN_WRITE_RESULT`。
4. **A9：批量修改复用第一次读取。** 每个有变更的条目只做读取、写入、读回三次本地请求，结果项包含读回的实体版本。未变化项为 `unchanged`，可带当前版本。保持首次失败即停止、后续为 `pending`；没有成功或未变化项时为 `failed`，否则为 `partial`；无法确认的写入为 `unknown`。版本读回失败不改变成功结果，只省略版本。
5. **A10（Agent 决定）：提示已接受写入的存储差异。** `add_items`、`create_note`、`update_item` 的结果项可带非空 `warnings` 字符串列表：非空提交字段在实际存储数据中缺失，或 `creators[n].creatorType` 被替换时，提示路径、条目类型和 `get_item_schema`。有 Extra 内容增量时说明这一事实，不凭缺失字段推断精确去向。字段值明确出现在其他存储字段时跳过，普通规范化不警告。创建复用响应的 `data`，更新复用读回的完整对象，不增加请求或 schema 查询；读回失败则没有版本和警告。不引入值类型校验。
6. **保持错误语义。** 写结果 `failed`、`unknown` 对应 MCP `isError=true`，`partial` 为 false。抛出错误的 envelope 仍为 `{ok:false,status,error}`。

## 理由

逐项表示提供输入位置、状态、恢复句柄和版本，足以支持实际调用者；重复聚合和完整原生对象没有独立恢复价值。严格输出模型同时缩小 outputSchema。版本是下一次修改的直接输入，应返回已存在的权威值而不是让调用者再查。

批量修改省掉的读取确实重复已有信息；写后读回则有实际用途，既提供实体版本，又能观察 Zotero 的字段存储行为。警告不把接受成功误报为失败，不复刻 Zotero 的值校验，也不为每种条目类型额外查 schema。

## 考虑过的选项

- **保留旧聚合字段作为兼容层：不采用。** 这是个人单用户工具，没有独立兼容消费者；保留会继续扩大响应与 schema。
- **直接暴露创建失败的数字码：不采用。** 调用者需要同一种字符串错误契约；原数字在 details 中仍可诊断。
- **使用 `Last-Modified-Version` 省掉写后读取：不采用，包括批量修改。** 实测有变更时条目更新为头 22/实体 22、集合 25/25、批量标签 27/27；无变化更新则为头 23/实体 22。更直接的反例是集合名称提交 `" Collection name "`、已有名称为 `"Collection name"`，Zotero 去除空格后没有变化，成功 PUT 的头为 31，实体仍为 29。仅本地比较提交值无法可靠判断 Zotero 规范化后的无变化写入；不为节省一次毫秒级本地 GET 复刻它的规范化规则。
- **上传后再读一次版本：不采用。** 74/75 反例表明 Zotero 在上传响应后仍会修改附件，立即读回也不能消除后续变更；附件创建后立刻编辑很少见，省略版本并要求编辑前主动读取更直接。
- **返回旧版本加一：不采用。** 库版本可以跨多次写入，不能推导实体版本。
- **按条目类型拒绝所有不匹配字段或值：不采用。** Zotero 有有效的基础字段映射及普通规范化；全面复刻需要额外 schema 请求和规则维护。针对已存储结果给出少量可操作警告，保留 Zotero 的实际接受行为。
- **回显全部已存储 data 供调用者比较：不采用。** 大多数写入不需要完整对象；警告仅在具体差异出现时携带简短信息，原生数据仍可主动读取。

## 重新评估的触发条件

- Zotero 修改创建响应，不再提供实体版本或实际存储 data，或上传结果不再表示上传后的实体版本。
- Zotero 提供明确的写后实体版本响应，不再依赖整个库的版本头。
- 实际恢复操作证明缺少某项信息；优先在错误 details 中加入必要上下文，而非恢复聚合回显。
- 真实使用出现未覆盖的静默丢失，或现有警告误报正常转换；用具体案例调整比较范围，不预建完整校验系统。
